## 2. 방식 A — Firestore Rules 검증

장착 필드의 **새 값**이 다음 중 하나일 때만 허용:
- 빈 값(장착 해제)
- 해당 슬롯의 **무료 기본 아이템 id**
- **기존** `resource.data.ownedItems` 에 `slot::id` 로 존재

### 위조 동시 시도 차단

`ownedItems` 는 이미 `usersRewardsUnchangedOnUpdate()` 로 잠겨 있다.
따라서 같은 update 에서 `ownedItems` 를 함께 위조하면 **그 update 자체가 거부**된다.
그럼에도 **`request.resource.data.ownedItems` 를 신뢰하지 않고 `resource.data` 를 기준으로** 판정한다
— 두 규칙이 서로를 전제하지 않게 해 한쪽이 약해져도 뚫리지 않게 한다.

`create` 시에는 `ownedItems` 를 실을 수 없으므로(`usersRewardsSafeOnCreate`)
장착 필드도 **무료 기본값 또는 빈 값만** 허용한다.

### stickers 처리 (Rules 에 반복문이 없다)

클라이언트가 최대 6개로 자르므로(`editStickers.slice(0, 6)`) **인덱스 0~5 를 명시적으로 검사**한다.
동시에 `size() <= 6` 도 Rules 에서 강제한다(클라만 믿지 않는다).
이모지→itemKey 매핑은 카탈로그에서 **생성**하고, 동기화는 테스트가 강제한다.

### 위험

| 항목 | 판단 |
|---|---|
| 배열·map 타입 | `stickers` 만 배열. 인덱스 검사 + size 상한으로 처리 |
| legacy 문서 | `resource.data.get('ownedItems', [])` 로 필드 부재 허용 |
| 문서 create | 무료 기본값·빈 값만 허용 |
| 관리자 작업 | `isAdmin()` 도 예외 없이 동일 적용(재화 필드와 같은 원칙) |
| 카테고리 혼용 | 슬롯별로 `slot::id` 를 만들어 검사 → `bg` 에 `pet` id 를 넣으면 거부 |
| Rules 크기·복잡도 | 생성 블록 약 4KB. 반복문 없이 슬롯 5 + 스티커 6 검사 |
| **카탈로그 동기화** | ⚠️ 상점에 아이템을 추가하면 Rules 도 재생성해야 한다 → **생성기 + 동기화 테스트**로 강제 |

## 3. 방식 B — 장착 전용 서버 endpoint

`/api/equip` 이 인증·소유권·슬롯·카테고리·개수를 검증하고 원자적으로 저장, Rules 는 장착 필드를 전면 잠금.

### 장점
- 카탈로그 단일 출처(`lib/shopItems.ts`)를 서버가 그대로 쓴다 → **Rules 에 카탈로그 사본이 없다**
- 이모지 역매핑·개수 제한을 코드로 자연스럽게 처리

### 단점 (이번 릴리스에서 결정적)
| 항목 | 영향 |
|---|---|
| **배포 순서** | endpoint → client → Rules **3단계**로 재설계 필요. 현재 확정된 client → Rules 2단계가 무너진다 |
| **client 재작성 필수** | `saveMyProfile()` 은 이름·소개·색·장착을 **한 번의 write** 로 저장한다. 장착만 endpoint 로 빼면 **프로필 저장이 2회 write 로 쪼개져** 부분 실패 UX 가 생긴다 |
| 구버전 client | endpoint 를 호출하지 않으므로 Rules 잠금 즉시 장착 저장 전면 실패 |
| offline | 현재 프로필 편집은 Firestore SDK 오프라인 큐를 탄다. endpoint 는 네트워크 필수 |
| operationId·원자성 | 여러 슬롯 동시 변경을 위한 별도 계약 필요 |
| rollback | 롤백 조합이 3계층 → 4계층으로 늘어난다 |

## 4. 결정 — **방식 A (Rules)**

### 이유

1. **client 변경이 0건이다.** 신규 client 의 선택 UI 는 이미 `isItemOwned()` 로 소유 아이템만 고르게 되어 있다.
   Rules 는 그 UI 계약을 서버에서 강제할 뿐이라 **정상 사용자 경험이 바뀌지 않는다.**
2. **배포 순서가 그대로다.** 이미 확정된 `client → Rules` 2단계에 얹힌다.
   방식 B 는 endpoint 를 먼저 배포하고 client 를 다시 만들어야 해 릴리스가 한 단계 늘어난다.
3. **마이그레이션이 없다.** 기존 문서의 값 형태를 바꾸지 않는다.
4. **롤백이 단순하다.** Rules 만 되돌리면 이전 동작으로 정확히 복귀한다.
5. 방식 B 의 유일한 실질 이점(카탈로그 단일 출처)은 **생성기 + 동기화 테스트**로 대체할 수 있다.

### 이번 범위에서 잠그는 것

| 슬롯 | 유료 개수 | 상태 |
|---|---|---|
| bg · frame · nameEffect · bannerEffect · pet | **134** | ✅ 잠금 |
| sticker | **89** | ✅ 잠금(이모지 역매핑) |
| **title** | 39 | ❌ **잠그지 않음** — §5 |

**223 / 262 유료 아이템(85%)** 이 서버 권위로 들어온다.

## 5. ⚠️ `title` 을 잠그지 않는 이유 (정직하게)

`title` 은 **자유 입력창**이다(`editTitle.slice(0, 24)`).
유료 title 아이템은 "미리 써둔 문구 프리셋"이고, 사용자는 원래부터 아무 문구나 직접 칠 수 있다.

- 유료 title 의 텍스트와 **같은 글자를 타이핑**하는 것을 Rules 로 막으려면
  **자유 입력 기능 자체를 없애야** 한다 → 이건 보안 결정이 아니라 **제품 결정**이다.
- 즉 title 은 "아이템 획득 우회"라기보다 **원래 열려 있는 기능**에 가깝다.

→ 이번 릴리스에서는 **범위 밖**으로 두고 문서화한다.
후속 과제: title 을 id 로 저장하도록 스키마를 바꾸고 자유 입력을 분리(`customTitle`)할지 제품 판단 필요.

---

## 6. 기존에 부정 장착된 데이터

Rules 는 **변경**을 막을 뿐 기존 값을 지우지 않는다.
이미 미소유 아이템을 장착해 둔 사용자는 그 상태가 유지되고, **다른 미소유 아이템으로 바꾸려 할 때 거부**된다.

- 정리(마이그레이션)는 이번 릴리스에 포함하지 않는다 — 사용자 데이터 일괄 수정은 별도 승인 사안이다.
- 규모 파악은 Rules 배포 후 읽기 전용 스캔으로 가능하다(후속).

## 7. 증명해야 하는 것 (테스트로 고정)

- `ownedItems` 와 장착 필드를 **같은 요청**으로 위조해도 실패
- localStorage 조작만으로는 장착 불가(서버 `ownedItems` 가 기준)
- 무료 기본 아이템 정상 · 실제 소유 아이템 정상 · 장착 해제 정상
- 다른 카테고리 itemKey · 존재하지 않는 itemKey 거부
- 정상 프로필 저장(이름·소개·색) 정상 · room·character·diary 등 무관 저장 정상
- 다른 사용자 문서 거부
- legacy 문서(ownedItems 필드 없음) 안전 동작
- 스티커 6개 초과 거부
