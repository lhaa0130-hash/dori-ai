## 2. 시나리오별 관측

### 순차 반복 (10회)
`mission_write_post_{오늘}` 을 10회 연속 → 첫 응답만 `duplicate:false`, 잔액 80, 원장 1건.

### 동시 10회 (여러 탭·네트워크 재전송)
10개 동시 요청 → 전부 200, 그중 `duplicate:false` **정확히 1건**.
나머지 9건은 `op.exists` 경로에서 rollback 후 저장된 결과를 반환하므로 **커밋 경합이 없다.**

### 동시 구매 10회
전부 200, 실제 과금 1건, `ownedItems` 1개, 구매 원장 1건, 원장 `resultingBalance` == 실제 잔액.

### 잔액 부족 경쟁
한 개만 살 수 있는 잔액으로 서로 다른 아이템 2개 동시 구매 → **422/200**.
한 건은 성공, 다른 건은 `insufficient_balance`. 보유 1개, 원장 1건, 잔액 음수 없음.

### 구매·보상 혼합 동시
구매 1 + 미션 1 + 업적 1 동시 → 전부 처리(적립 90, 차감 20), `잔액 == 5000 + 90 − 20`.

### 전역 상한 경쟁
`candyDailyTotal` 을 560 으로 세팅(여유 40) 후 30+50+? 를 동시 청구 →
**요청 합 90 인데 40 만 지급**, 집계 정확히 600(=`DAILY_CANDY_TOTAL_CAP`), 원장 합계 == 잔액.

### ★ 문서 삭제 후 재청구(파밍 시도)
1. 미션 청구 성공 → 2. `users/{uid}` **삭제** → 3. 하위 컬렉션 원장은 **살아남음**(Firestore 계약 실측) →

## 3. 🟡 발견 P2 — 동시 요청 livelock (감사 브랜치에서 수정)

### 증상
Phase 5 최초 실행에서 "동시 2~3건" 시나리오가 **전부 409** 로 끝났다.
데이터는 안전했지만(원장↔잔액 정합 유지) **정당한 작업이 함께 실패**했고,
그 결과 테스트가 `0 == 0` 형태로 **공허하게 통과**하고 있었다.

### 원인
재시도 루프가 `commit_conflict` 를 만나면 **즉시** 다음 시도를 했다(백오프·지터 없음).

```ts
if (e?.code === "commit_conflict") continue;   // ← 대기 0
```

같은 `users/{uid}` 문서를 동시에 갱신하는 요청들이 매번 같은 타이밍에 재시도해
서로를 밀어내고 3회를 모두 소진했다.

### 계량 (수정 전)

| 동시 | 지연 | 성공 | 409 | 원장↔잔액 |
|---|---|---|---|---|
| 2 | 0ms | 1.7/2 | 0.3 | ✅ |
| 3 | **0ms** | **1.0/3** | **2.0** | ✅ |
| 2·3 | ≥50ms | 전부 성공 | 0 | ✅ |

→ **안전성은 어떤 조건에서도 깨지지 않았다.** 순수 가용성 문제.

### 수정 (`functions/_shared/firestoreRest.ts`)

```ts
export function conflictBackoffMs(attempt, rand = Math.random()) {
  const base = Math.min(40 * Math.pow(2, attempt), 160);
  return Math.round(base * (0.5 + rand));   // 지터 0.5x~1.5x, 상한 300ms
}
```

`claim-reward`(3곳) · `purchase`(1곳) · `admin/grant`(1곳) 의 재시도 지점 **5곳**에
`await waitBeforeRetry(attempt)` 삽입. 계약 테스트 `tests/conflict-backoff.test.ts` 6종 추가
(상한 300ms · 지수 증가 · 지터 폭 · 총 대기 1초 이하).

### 계량 (수정 후)

| 동시 | 지연 0ms 성공률 |
|---|---|
| 2 | **2.0/2** |
| 3 | **3.0/3** |
| 종합 | **59% → 100%** |

### 등급 근거
- 임의 재화 획득·원장 우회·권한 우회 **아님** → P0 아님
- 중복 지급·상한 우회 **아님**(안전성 유지) → P1 아님
- 정당한 작업이 실패하고 사용자는 재시도(아웃박스)로 복구 → **P2**
- 다만 **모니터링에서 409 스파이크로 보일 수 있어** 배포 전 반영을 권고한다

> ⚠️ 이 수정은 **감사 브랜치에만** 있다. main·Production 에 적용하지 않았다.
> 별도 PR 로 검토받아야 한다(§5 참조).

## 4. 관측 못 한 시나리오 (정직하게)

| 시나리오 | 상태 | 사유 |
|---|---|---|
| 원장 생성 후 응답 직전 실패 | **미검증** | Firestore 커밋 후 응답 유실은 클라이언트에서 재시도 → `duplicate` 로 수렴. 서버측 주입 지점이 없어 로컬에서 재현 불가 |
| 잔액 변경 후 원장 실패 / 원장 후 잔액 실패 | **구조적으로 불가** | 둘이 **한 커밋**의 writes 배열에 함께 들어간다. 부분 반영 경로가 없다 |
| Firestore 실제 contention(운영 규모) | **미검증** | 에뮬레이터 기준. 운영은 낙관적 동시성 특성이 다를 수 있다 → 배포 후 409 비율을 모니터링(Phase 14) |
| notification 생성 실패 | **해당 없음** | 신규 경로는 알림을 지급 근거로 쓰지 않는다(P0 #6 제거) |

## 5. 후속

이 백오프 수정은 **cottonCandy 릴리스와 독립적**이다. 두 가지 선택지:

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (권고)** | 현재 릴리스 그대로 배포하고, 백오프는 별도 PR | 릴리스 범위 불변, 검증된 코드 그대로 | 초기에 409 가 조금 보인다 |
| B | 백오프를 릴리스에 포함 | 409 스파이크 없음 | 배포 직전 코드 변경 = 재검증 필요 |

**A 를 권고한다.** 현재 Functions 는 이미 Production 에 있고, 백오프는
사용자 체감 개선이지 보안 수정이 아니다. 카나리에서 409 비율을 관측한 뒤 결정해도 늦지 않다.
